  1. 1 / 3

    kubectl answers one question at a time.

    Which pods are failing? Where do they run? Why did the last one die? Every answer is another command, another -n flag, another wall of text to scan while the pager keeps buzzing.

  2. 2 / 3

    A monitoring stack is a project of its own.

    Exporters on every node, a metrics database, storage, dashboards to build. Worth it for alerting and history. A lot to stand up when you only need to see what's going on right now.

  3. 3 / 3

    Admin dashboards make production nervous.

    A tool that can edit and delete is one misclick from the next incident, and a hard sell to whoever owns the cluster.

02The solution

Opscope is the glance.

One page that tells you what's healthy, what needs attention and where to look next. Click through to any object for its YAML, events and logs.

  1. 1
    What needs attentionA health chip counts what's wrong, broken down on hover.
  2. 2
    Live usageCPU and memory from metrics-server, with the last 15 minutes.
  3. 3
    Every kind, at onceHealthy against not, for each workload and Gateway API type.
  4. 4
    Every nodeStatus, role, version and usage against what's allocatable.

1page

Instead of six commands.

Health, nodes, pods, usage and recent warnings, top to bottom. Statuses are worked out like kubectl get pods, so crash loops show up as crash loops.

42MB

Instead of a stack.

One Docker image with a Go server and the web app inside. No agents on your nodes, no database, nothing to operate.

2verbs

Instead of admin rights.

Opscope uses get and list. Nothing else. Its ClusterRole couldn't create, patch or delete if it tried.

04Install

From zero to overview in one command.

Pick where Opscope runs. Every way ends at localhost:8080. Add metrics-server to the cluster if you want usage numbers.

  1. Run the image. The port stays on 127.0.0.1, and saved clusters live in a volume.

    docker run --rm -p 127.0.0.1:8080:8080 -v opscope-data:/data ghcr.io/unnikrishnannam/opscope:latest

  2. Open localhost:8080, choose Add a cluster and paste a kubeconfig. This prints one for your current context:

    kubectl config view --minify --flatten

  1. Apply the manifests: a namespace, a read-only ClusterRole, the Deployment and a Service.

    kubectl apply -f https://raw.githubusercontent.com/unnikrishnanNam/OpScope/main/deploy/kubernetes/opscope.yaml

  2. Optional: let it read Secrets. Leave this out and only the Secrets pages are off.

    kubectl apply -f https://raw.githubusercontent.com/unnikrishnanNam/OpScope/main/deploy/kubernetes/secrets-access.yaml

  3. Reach it through a port-forward. The cluster shows up as “this cluster”.

    kubectl -n opscope port-forward svc/opscope 8080:80

  1. Clone the repository.

    git clone https://github.com/unnikrishnanNam/OpScope.git && cd OpScope

  2. Build the image and run it. Or make build for a local binary, with Go 1.26+ and Node.js 24+.

    make docker-build && make docker-run

05Fine print

The fine print, up front.

There's no login.

Anyone who can open the page can read what Opscope can read. Keep it on 127.0.0.1, reach it through kubectl port-forward, or put an auth proxy such as oauth2-proxy in front.

Reading Secrets is opt-in.

In a cluster, Secrets access is its own ClusterRole. Delete that one file and the Secrets pages say they aren't allowed. Everything else keeps working.

A glance, not a time machine.

Usage history is 15 minutes, kept in memory. For alerts and long-term metrics, keep your monitoring stack. Opscope sits happily next to it.
